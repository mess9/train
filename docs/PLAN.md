# План имплементации

Обновлено: 2026-11-01. Концепция — [DESIGN.md](../DESIGN.md), термины — [CONTEXT.md](../CONTEXT.md),
решения — [adr/](adr/), макет — https://claude.ai/artifact/REmzMBaPjSzQf8PcUU9LkS

Цель первого среза («вечер»): агент через CLI создаёт план → владелец проходит его на телефоне,
в том числе без сети → агент получает `gym compare`. Всё, что не нужно для этого цикла, — потом.

## Стек

| Что | Чем |
|---|---|
| Сборка | Gradle (Kotlin DSL) + version catalog, JDK 21, актуальные стабильные Kotlin 2.x / Quarkus 3.x / Compose Multiplatform |
| `core` | KMP (jvm + wasmJs): DTO на kotlinx.serialization, UUIDv7, логика `compare`; без HTTP |
| `client` | KMP (jvm + wasmJs): API-клиент на Ktor для `cli` и `app` — на сервер Ktor не попадает |
| `server` | Quarkus: `quarkus-rest` + `quarkus-rest-kotlin-serialization`, `hibernate-orm-panache-kotlin`, Flyway, SmallRye OpenAPI, Dev Services (Postgres в dev) |
| `cli` | JVM, Clikt + API-клиент из `client`, `installDist` → скрипт `gym` |
| `app` | Compose Multiplatform, таргет wasmJs; API-клиент из `client`; `sw.js` и manifest — руками |
| БД | Postgres 16+ |

Вся аналитика живёт в `core` и выполняется на сервере. CLI и приложение только показывают её
результат (ADR 0002).

## Шаг 0. Проверка Compose/Wasm на телефоне (~30–60 мин)

Минимальное приложение: экран с карточкой упражнения, три поля чисел, кнопки оценок, список
на 30 строк. Сборка `wasmJsBrowserDistribution` отдаётся любым статическим сервером.

Проверить на Android Chrome (спайк — `spike/`, выложен на https://train.fil-lost.org):
- [x] кириллица рендерится шрифтом по умолчанию, жирный тоже;
- [x] цифровая клавиатура: `KeyboardType.Decimal` и `Phone` — да; `Number` и `NumberPassword` —
  обычная текстовая. В приложении все числовые поля — `Decimal` (цифры, `,` `.` `-`), лишние
  символы отсекаются в `onValueChange`: клавиатура не гарантирует, что придут только цифры;
- [x] прокрутка — «не очень, но сойдёт»; вернуться, если на реальном экране тренировки будет мешать;
- [x] установка на главный экран; после закрытия Chrome запуск с иконки поднимает данные;
- [ ] запуск с иконки в режиме полёта (service worker);
- [ ] wake lock держит экран;
- [ ] холодный старт — не больше пары секунд;
- [x] анимированный gif: `<img>` поверх canvas с `blob:`-URL, полученным запросом с заголовком;
- [x] Ktor-клиент в Wasm с `followRedirects = false` на редирект возвращает `status=0`
  (fetch — `opaqueredirect`), без сети — бросает исключение: вход в Access отличим от офлайна;
- [x] Web Locks API: вторая вкладка не получает лок;
- [x] запись в localStorage переживает закрытие приложения.

**Важно про HTTPS.** Service worker и wake lock работают только в secure context. Спайк
отдаётся через туннель Cloudflare на `train.fil-lost.org` (контейнер `train-spike`, см.
`spike/deploy/`); настоящий `train` потом займёт этот же адрес.

### Выводы спайка — учесть в шагах 1, 5, 6

- **Cloudflare переписывает `Cache-Control`.** Сервер отдаёт `no-cache`, браузер получает
  `max-age=14400` (Browser Cache TTL зоны) и 4 часа держит старый JS. Поэтому: все файлы,
  кроме `index.html` и `sw.js`, — с хешем в имени (`spike.js` webpack сейчас без хеша); service
  worker берёт оболочку `fetch(…, {cache: 'no-cache'})`; либо Cache Rule для `train.fil-lost.org`
  «Browser TTL: respect origin».
- **Стратегия service worker:** файлы с хешем — сначала кэш; `index.html` — сначала сеть с
  коротким таймаутом, потом кэш; имя кэша меняется со сборкой, старые кэши удаляются в
  `activate`. Сплошное «сначала сеть» офлайн добавляет к первому кадру ожидание неудачного запроса.
- **Wasm весит 11 МБ** (8,3 skiko + 2,7 приложение). Cloudflare сам сжимает в brotli; локально
  без него — сжимать на сервере.
- **Web Lock брать в JS до старта Compose**, не в `LaunchedEffect`: фоновая вкладка не рисует
  кадры, и лок не запрашивается.
- **Глобальное имя webpack** = `outputModuleName`: свои JS-глобалы называть иначе (`bridge`).
- Своё состояние в JS, Kotlin читает строкой через `status()` — без колбэков через границу Wasm.
  Для спайка хватило, для приложения так же.

Не прошла хотя бы одна проверка и это не чинится быстро → в `app` добавляется таргет Android,
UI-код тот же (ADR 0003). Остальной план от этого не меняется.

## Шаг 2. `core`: модель и общая логика

- DTO по модели DESIGN.md: `Exercise` (+ `implements: 1|2`), `RecordType` (`WEIGHT_REPS`, `REPS`,
  `TIME`, `WEIGHT_TIME` + `perSide`), `Plan` (+ `version`) / `PlanBody` / `Block` / `BlockItem` /
  `TargetSet`, `Workout` (+ `planVersion`) / `WorkoutLayout` (снимок целей, `replacedFrom`) /
  `SetFact` (свои `exerciseId`, `recordType`, `perSide`; `done`, `deleted`) / `Rating`,
  `Measurement`, `Profile`.
- Синхронизация (ADR 0007): у синхронизируемых записей `rev`, в запросе — `baseRev` и `opId`.
  `Outbox` — последнее состояние каждой записи, схлопывание, правило «кто побеждает».
- Вес — одного снаряда, повторы «на сторону» — на каждую сторону; `Volume` = вес × снарядов ×
  повторы × (2, если «на сторону»).
- `Passes` — текущий проход, следующая строка карточки, «проход закрыт» → какой отдых (DESIGN,
  экран тренировки).
- Значения необязательны: неизвестное — `null`, не ноль.
- `newId()` — UUIDv7, генерация на клиенте.
- `Prefill` — правило предзаполнения: цель плана → прошлый факт на том же номере подхода.
- `Compare` — план против факта: по каждому целевому подходу цель / факт / оценка / отметка;
  добавленные, пропущенные и заменённые подходы; итоги (время, объём, темп); прошлые результаты
  этих упражнений.
- `ApiClient` (Ktor) — в модуле `client`, общий для `cli` и `app`.
- Юнит-тесты на `Prefill`, `Compare`, `Passes` (неровный круг, пропуски, добавленный подход) и
  `Outbox` (отметил → снял → отметил; повтор после потерянного ответа).

**Сделано 2026-11-03.** Код — `core/src/commonMain/kotlin/train/core/`, 34 теста на JVM. Решения
по ходу:
- `kotlin.uuid.Uuid` и `kotlin.time.Instant` — из stdlib (в Kotlin 2.4 стабильны), сериализуются
  kotlinx.serialization. `Uuid.generateV7()` ещё экспериментальный — обёрнут в `newId()`.
  Дата плана — `LocalDate` из kotlinx-datetime 0.8.0; в Wasm он тянет npm `@js-joda/core`
  (обновлён `kotlin-js-store/wasm/yarn.lock`).
- `TrainJson`: отсутствующее поле — `null`, `null` в ответ не пишется (короче для агента).
- ID блоков, упражнений плана и целей во входном JSON необязательны — генерируются при разборе.
- Раскладка тренировки — свои типы (`LayoutBlock`, `LayoutItem`): тип записи и сторона уже
  разрешены из справочника (`PlanBody.snapshot`), есть `replacedFrom`, `added`, `removed`. Цели
  в раскладке не меняются.
- «Убрать подход» = факт с `deleted` на этом номере: строка прячется, плановый подход в `compare`
  — `SKIPPED`. «+ подход» = факт без цели со следующим номером.
- Предзаполнение диапазона повторов — верхняя граница. Поля берутся только те, что есть у типа
  записи.
- Отдых после закрытого прохода; не задан у блока → отдых упражнения (иначе у блока из одного
  упражнения таймера не было бы).
- Нагрузка — три числа (DESIGN, «Аналитика»): `volumeKg` с долей веса тела (`bodyweightFactor`
  у упражнения, вес тела — параметр `compare`), `workSets`, `timeUnderLoadSec`. Неизвестный
  объём не считается нулём: такие подходы — в `volumeUnknownSets`. Темп — `paceSecPerKg`.
- `compare` отдаёт подходы коротко (`DoneSet`, без служебных полей); `exerciseId` у подхода —
  только если он сделан до замены. Факты без места в раскладке — в `unplaced`, не теряются.
- `Outbox`: `baseRev` — это `rev` записи в очереди; правка поверх неотправленного — новый
  `opId` с прежней базой; ответ на старый `opId` переносит базу, но запись не снимает.

## Шаг 3. `server`

**Схема (Flyway `V1__init.sql`)**, ADR 0006:

| Таблица | Поля (главное) |
|---|---|
| `app_user` | id, email, name, `profile jsonb` (оборудование и пр.) |
| `api_key` | id, user_id, `key_hash`, label, revoked_at |
| `exercise` | id, owner_user_id (null = общий), source_id, name_ru, name_en, muscles_primary, `muscles_secondary jsonb`, equipment, implements, bodyweight_factor, record_type, per_side, media_key, `instructions jsonb`, deleted_at |
| `plan` | id, user_id, date, title, version, started_at, started_version (`< version` — правка не применилась), deleted_at |
| `plan_revision` | plan_id, version, `body jsonb`, created_at — неизменяемые |
| `workout` | id, user_id, plan_id, plan_version, started_at, finished_at, comment, `layout jsonb` (снимок), rev, op_id, deleted |
| `workout_set` | id, workout_id, user_id, exercise_id, record_type, per_side, block_id, item_id, set_no, target_id, weight, reps, extra_weight, seconds, rating, note, done, done_at, received_at, rev, op_id, deleted |
| `measurement` | id, user_id, type, value, unit, measured_at, workout_id, rev, op_id, deleted |
| `revision_log` | entity, entity_id, rev, `data jsonb`, replaced_at — перезаписанные версии |

Индексы: `workout_set (user_id, exercise_id, done_at desc)` для «прошлого результата»;
`plan (user_id, date)`.

**Авторизация** (ADR 0008). Фильтр по заголовку `X-Api-Key`: хеш → пользователь в контексте
запроса. Если есть `Cf-Access-Jwt-Assertion`, почта из него должна совпасть с владельцем ключа
(включается вместе с Cloudflare). Все запросы фильтруются по `user_id`. Первый пользователь и ключ —
из окружения при старте (`TRAIN_BOOTSTRAP_EMAIL`, `TRAIN_BOOTSTRAP_KEY`).

**API** (`/api`, схема на `/q/openapi`):

| Метод | Что |
|---|---|
| `GET /exercises?q=` | справочник; сначала недавние |
| `POST /exercises` | добавить из источника: `{sourceId, nameRu, recordType?}` |
| `PATCH /exercises/{id}` | правка (ru-название, тип записи, мышцы) |
| `GET /source/exercises?q=` | поиск по всему датасету |
| `GET /exercises/last-sets?ids=` | последние факты по упражнениям — для «прошлого» и предзаполнения |
| `GET /plans?from=&to=` · `GET /plans/{id}` | планы; статус `planned` / `overdue` / `started` вычисляется |
| `PUT /plans/{id}` | создать или заменить → новая версия; после старта — `409` |
| `DELETE /plans/{id}` | в корзину |
| `GET /workouts?from=&to=` · `GET /workouts/{id}` | тренировки с подходами |
| `PUT /workouts/{id}` | upsert: старт (`planVersion` и снимок; фиксирует `plan.started_at`, при другой версии — пометка), `layout`, финиш, комментарий |
| `PUT /workouts/{id}/sets/{setId}` | upsert полного состояния с `baseRev` + `opId`; снятие отметки и удаление — `done` / `deleted` |
| `GET /workouts/{id}/compare` | план против факта (`core.compare`); вес тела — последний замер `weight` до старта |
| `GET/PUT /measurements/{id}` · `GET /measurements` | замеры (тот же протокол) |
| `GET/PUT /profile` | профиль: оборудование, настройки |
| `GET /trash` · `POST /trash/purge` | корзина и окончательное удаление |
| `GET /me` · `POST /keys` · `GET /keys` · `DELETE /keys/{id}` | владелец ключа; новый ключ, список, отзыв |

Синхронизация — по ADR 0007:
- тот же `opId` → `200` без изменений;
- устаревший `baseRev` → `409` с текущим состоянием;
- в активной тренировке клиент повторяет запрос с новым `baseRev`, перезаписанное уходит в
  `revision_log`;
- вторую активную тренировку сервер не отвергает — принимает и помечает.

**Источник и медиа.** Путь к `exercises.json` — `train.source.path`; файл загружается в память
при первом поиске. Медиа-пакет — отдельная папка (`train.media.path`), отдаётся по
`GET /media/{media_id}.jpg|.gif`; имена файлов как в датасете, `0289-xxxx.jpg`, файлы ищутся в
корне папки и в `images/` / `videos/`. Нет файла → `404`, клиент рисует заглушку.

Готово, когда проходят REST-тесты (`@QuarkusTest`):
- цикл план → старт → подходы → финиш → compare;
- повтор с тем же `opId` ничего не меняет; устаревший `baseRev` → `409`; старая отправка не
  воскрешает удалённую запись;
- старт с версией 1 после правки плана до версии 2 → тренировка принята, план помечен, compare
  идёт по снимку;
- чужой ключ не видит чужое;
- отозванный ключ получает `401`.

**Сделано 2026-11-03.** Код — `server/src/main/kotlin/train/server/`, 14 тестов (`ApiTest`,
`InfoResourceTest`) на Postgres из Dev Services. Решения по ходу:
- Хранение — JDBC через тонкий `Db` (без Hibernate/Panache): тело плана и раскладка — jsonb,
  запросы короткие, а сущности ORM дублировали бы модель `core`. В `@Transactional` все запросы
  идут одним соединением, `for update` держит строку.
- Протокол ADR 0007 — общий `sync()` для тренировок, подходов и замеров. Ответ — запись, как она
  легла в базу (время — до микросекунд), поэтому повтор с тем же `opId` возвращает то же самое.
- Первый пользователь — переменными окружения при старте, `gym admin init` не нужен; в `%dev` —
  `dev@local` / `dev-key`. Новый ключ — `POST /api/keys`, показывается один раз, хранится хеш
  SHA-256. Ключи выпускает и отзывает только владелец своих ключей; отозванный получает `401`,
  отозванный bootstrap-ключ при рестарте не возвращается — нужен новый в окружении.
- Открыты без ключа только `/api/info`, оболочка приложения и `/q/*`. Медиа — по ключу:
  приложение грузит картинки своим HTTP-клиентом.
- План: ID блоков, упражнений и целей не повторяются, упражнения — из справочника пользователя,
  иначе `400`. Запись в удалённый план возвращает его из корзины. План, который окончательно
  удалили, пока телефон был без сети, тренировку не ломает: она принимается без `planId`.
- `GET /exercises/{id}`, `GET /source/exercises/{id}` — добавлены; `PATCH` — только своих
  упражнений. Поиск по датасету: каждое слово запроса — в названии, мышцах, части тела или снаряде.
- Корзина: `purge` удаляет планы, тренировки (с подходами) и замеры из корзины; удалённые подходы
  живых тренировок остаются — иначе старая отправка воскресила бы подход.
- «Сегодня» для статуса плана и границы дней в фильтрах — по `train.zone` (по умолчанию пояс
  системы).

## Шаг 4. CLI `gym`

Конфиг: `GYM_URL`, `GYM_API_KEY` или `~/.config/gym/config`. Вывод — JSON (ADR 0005).

```
gym [--url …] [--pretty] <команда>
gym info | me
gym plan put <file.json|-> [--id] # создать или заменить план
gym plan list [--from --to]
gym plan get <id>
gym plan rm <id>
gym workout list [--from --to]
gym workout get <id>
gym compare <workoutId>
gym exercise list [--q]
gym exercise get <id>
gym exercise search <q…> [--limit] # по всему датасету
gym exercise add [<sourceId>] --ru "..." [--type ... --implements --per-side ...]
gym exercise edit <id> [поля как у add]
gym exercise last <id…> [--exclude <workoutId>]
gym measure list [--type --from --to]
gym measure add <type> <value> [--unit kg] [--at ISO]
gym profile get | put <file|->
gym trash list | purge --yes
gym admin key [--label] [--qr]    # новый ключ; --qr — ссылка …/#key=… для телефона
gym admin keys | revoke <id>
```

**Сделано 2026-11-03.** Код — `cli/src/main/kotlin/train/cli/`, 11 тестов (`CliTest`) на Ktor
MockEngine. Решения по ходу:
- Настройки: флаг → переменная окружения → файл (`GYM_CONFIG` — другой путь). Файл — строки
  `ключ=значение`: `url`, `key`, `cf_client_id`, `cf_client_secret`. Сервисный токен Cloudflare
  Access — ещё `GYM_CF_CLIENT_ID`, `GYM_CF_CLIENT_SECRET`, для агента на другой машине. Редиректы
  не следуются: редирект — это страница входа Access, о ней и ошибка.
- Ошибка — одна строка JSON `{"error", "status"}` в stderr и код выхода 1; ошибка аргументов —
  текст clikt с подсказкой, тоже код 1. `409` у `plan put` — «план уже начат».
- `plan put` берёт ID из `--id`, иначе из поля `id` в файле, иначе новый: вывод `plan get` можно
  поправить и отправить обратно — выйдет новая версия того же плана.
- `measure add` — новая запись (`baseRev = 0`); `trash purge` без `--yes` ничего не делает.
- `admin key --qr` рисует QR в stderr, чтобы stdout оставался JSON. `gym admin init` не нужен:
  первый пользователь — из окружения сервера (шаг 3).
- `ApiClient` в `client` — общий с приложением: `PutResult.Accepted | Conflict` для записей с
  версией, `ApiException` для остального.

## Шаг 5. Приложение (PWA)

Экраны — по макету: главная, план, тренировка, техника, завершение, история (список и детали),
замеры. Навигация — свой `sealed class Screen`, без библиотеки.

Состояние и офлайн:
- `Storage` — интерфейс в `core`, в браузере реализован через `localStorage` (ADR 0007). Два ключа:
  - `session` — активная тренировка + очередь; пишется одним `setItem` на действие, до
    обновления экрана;
  - `cache` — планы на 2 недели и `last-sets` их упражнений; потерять не страшно.
- Очередь — последнее состояние каждой записи с `baseRev` и `opId`, привязана к `userId`.
  Досылается, когда есть сеть. В шапке значок «не отправлено: N».
- Писать может только вкладка с Web Lock `active-workout`; вторая показывает «открыто в другой
  вкладке».
- Экран «Подключение»: ключ вставкой или из `#key=` в ссылке QR; смена — в настройках.
  Состояния связи: офлайн / нужен вход в Cloudflare / ключ не принят / ошибка сервера (ADR 0008).
- Картинки и gif грузятся HTTP-клиентом с ключом; gif — `<img>` с `blob:`-URL.
- В dev-сборке — переключатель «пауза отправки», чтобы проверить окно «отметил, а сервер ещё не
  знает».
- Активная тренировка восстанавливается после перезапуска; забытая предлагается закрыть
  временем последней отметки + 5 мин.
- `sw.js`: предкэш оболочки (wasm, js, шрифт); медиа кэшируются при первом показе.
- Wake lock — через JS interop, запрашивается при старте тренировки и снова при возврате на
  вкладку.

Экран тренировки — по DESIGN.md и макету: блоки с оттенками, свёрнутые карточки со строкой
следующего подхода, тап по оценке = отметка, повторный тап снимает, полоска отдыха из плана,
таймер / секундомер, меню упражнения, режим порядка, «+ упражнение» из справочника (сначала
недавние), смена типа записи на месте.

Готово, когда на телефоне в режиме полёта проходится вся тренировка, а после включения сети
`gym compare` показывает все подходы. И ещё: пауза отправки → отметка → убить приложение →
открыть → снять паузу → подход на сервере.

**Сделано 2026-11-03.** Код — `app/src/wasmJsMain/`: `AppState` (стек экранов, очередь, связь),
`Home`, `WorkoutScreen`, `Screens` (техника, завершение, история, замеры), JS-мост в `index.html`.
Проверено в headless Chromium на 375×812, не на телефоне: офлайн-загрузка из SW, отметки без сети
и досылка, пауза → отметка → перезагрузка → снять паузу → подход на сервере, замена, порядок, смена
типа, завершение с комментарием, замеры, забытая тренировка. Решения по ходу:
- Cloudflare переписывает `Cache-Control` на 4 часа, поэтому `server:appDist` хеширует `app.js`
  (wasm хеширует webpack), подставляет имя в `index.html`, а в `sw.js` — номер сборки и список
  файлов. SW: оболочка из кэша, `index.html` — сначала из сети, медиа — кэш при первом показе,
  `/api/` мимо. Новая сборка подхватывается со второй перезагрузки. Иконки и манифест без хеша —
  меняются редко.
- Web Lock ждём до 2 с, а не `ifAvailable`: при перезагрузке старый документ отпускает замок не
  сразу, и вкладка ошибочно считала себя второй.
- В очереди `SyncRecord` полиморфный с дискриминатором `kind`: `type` — поле замера, с ним
  сериализация падала.
- Отдых в памяти, после перезагрузки полоска пропадает; отметки — в `session`.
- Мышцы из датасета переводятся словарём в приложении; незнакомые — как есть.
- Пауза отправки — в настройках любой сборки, раздел «Проверка».

Не сделано в MVP: две активные тренировки на разных устройствах (план, начатый на другом, — «не
закончена», вести её отсюда нельзя); «Изменить» в истории; вибрация не смотрит на
`Profile.vibration`; фото в замерах. Проверка на телефоне в режиме полёта — при развёртывании.

## Шаг 6. docker-compose

Сразу в формате mediabots, чтобы потом подключить CI без переделки:
- `compose.yaml` (проект `train`): `server` + `postgres` с томом;
- `server` — образ из multi-stage `Dockerfile` (Gradle-сборка + Quarkus JVM);
- монтируются папка медиа-пакета и `exercises.json`, только чтение, по абсолютным путям хоста;
- секреты (пароль БД, начальный ключ) — `${VAR:?}` из env-файла, образец — `train.env.example`;
- healthcheck — `/q/health`.

Бэкап — пока ручной `pg_dump`, команда в README.

## Шаг 7. Агент и данные

- Скилл `skills/gym/SKILL.md`: рабочий цикл (план → факт → compare → следующий план), команды CLI,
  JSON-пример плана с блоками, ролями, пирамидой, отдыхом и типами записи. Правила: план после
  старта не трогать; просроченные — решать явно; неизвестное — `null`.
- Стартовый справочник: агент смотрит историю Hevy / GymKeeper и оборудование, подбирает
  несколько десятков упражнений через `gym exercise search` и добавляет с ru-названиями.
- Первый настоящий план на ближайшую тренировку.

## Порядок и параллельность

Шаг 0 идёт первым и в одиночку — от него зависит, на чём делать `app`. Затем каркас и DTO
`core` (шаги 1–2). После этого параллельно можно вести две ветки: `server` + `cli` (шаги 3–4) и
`app` (шаг 5, сначала на заглушке API). Сходятся они на шаге 6, на проверке среза. Шаг 7 нужен
только для CLI.

## Проверка среза

1. `gym plan put` — план с разминкой, кругом × 3 и заминкой на сегодня.
2. Телефон: план виден, «Начать», включить режим полёта, пройти часть подходов, одну правку
   значений, одну замену упражнения, добавить подход, убить приложение посреди тренировки.
3. Открыть снова — тренировка на месте. Выключить режим полёта, завершить с комментарием,
   записать замер.
4. `gym compare` — видны все подходы, отметки времени, заменённое и добавленное.
5. Окно до подтверждения: пауза отправки → отметить подход → убить приложение → открыть →
   подход на месте → снять паузу → подход на сервере, ровно один.
6. Офлайн-старт против правки: телефон закэшировал план и офлайн начал тренировку, а агент тем
   временем сделал `gym plan put` новой версии → после синхронизации тренировка цела, план
   помечен, compare идёт по тому, что было на экране.
7. Скакалка: подход 1 по времени, смена типа на повторы, подход 2 → в compare у каждого свой тип.

## Следующие итерации

Примерно в порядке пользы:
1. **CI/CD по образцу `c:\java\my\mediabots\`.** Репозиторий `mess9/train` в Gitea. В Jenkins —
   pipeline из SCM, credential `gitea-registry`.
   - `Jenkinsfile`: сборка образа → тесты → push в `localhost:5000/mess9/train-server` (номер
     сборки и `latest`) → `docker compose up -d --remove-orphans` с credential `train-env` →
     smoke-тест (контейнеры healthy и не перезапускаются) → webhook в n8n.
   - `@QuarkusTest` с Postgres в CI — Testcontainers через docker socket; проверить при
     настройке.
2. **Доступ снаружи**: Cloudflare Tunnel + Access (Google / почта для телефона, сервисный токен
   для CLI), почта из JWT → пользователь.
3. **Импорт истории** Hevy / GymKeeper:
   - Codex через MCP выгружает в файлы всё доступное.
   - Claude конвертирует в JSON формата API и заливает через `gym import <dir>`: планы,
     тренировки с подходами, замеры. Планы связываются со своими тренировками.
   - ID — UUIDv5 от (источник, исходный ID), поэтому повторная заливка безопасна.
   - Чего по MCP не достать — владелец вписывает вручную в тот же JSON.
4. **Статистика**: коэффициенты объёма и канонический список мышц — на импортированной истории.
   - `gym volume --period` (по умолчанию месяц).
   - В приложении экран статистики: звёздчатая диаграмма по частям тела и схема тела спереди и
     сзади. Подсветка мышц тем ярче, чем больше нагрузки за период.
   - Нужна SVG-схема тела с отдельными областями мышц — найти со свободной лицензией или
     нарисовать.
5. **Фото**: Garage + `quarkus-amazon-s3`, съёмка после тренировки.
6. **Оборудование**: подсказка собираемых весов.
7. **Экспорт** всего в JSON/CSV по пользователю, бэкап по расписанию.
8. Поиск по датасету с телефона, дистанция в типах записи.
9. Потом и по необходимости: MCP, Telegram-бот, обмен между пользователями, редактор планов,
   свободная тренировка.
