# 0009. Версия: semver и коммит

Дата: 2026-11-05. Статус: принято.

## Решение

- У проекта одна версия на всё — сервер, приложение, CLI: `version` в `gradle.properties`
  (semver, сейчас `0.2.0`). Поднимает её человек вместе с изменением, которое стоит назвать.
- `core` генерирует из неё `TRAIN_VERSION` (`build/generated/version`) — константу видят
  сервер, приложение и CLI без чтения ресурсов.
- Полная версия — `<semver>+<коммит>`, например `0.2.0+5cdae85` (`fullVersion` в `core`).
  Коммит знает только сборка образа: Jenkins передаёт `--build-arg TRAIN_COMMIT=$(git rev-parse
  --short HEAD)` и `TRAIN_BUILD=$BUILD_NUMBER`, в образе это переменные окружения. Вне образа
  коммита нет — `0.2.0+dev`.
- `GET /api/info` → `{name, version, commit?, build?, app?}`: `version` — полная, `build` —
  номер сборки Jenkins, `app` — хеш сборки приложения, которое раздаёт сервер.
- В приложении «Настройки → Версия»: приложение — `TRAIN_VERSION` и хеш его сборки; если на
  сервере та же сборка, то полная версия сервера. `gym info` выводит `ServerInfo` как есть.

## Почему

Хеш сборки приложения говорит «устарело», но не говорит «что именно стоит». Номер сборки
Jenkins не связан с кодом. semver читается человеком и агентом, а коммит однозначно указывает
на код. Одна версия на всё: модули собираются и выкатываются вместе одним образом.

## Отвергнуто

- **Версия из `git describe` в Gradle.** В Docker-сборке нет `.git` (и не нужно), а локально
  она зависела бы от тегов, которых нет.
- **Коммит в ресурсе при сборке Gradle.** Тот же `.git`; вдобавок ломает кэш Gradle на каждом
  коммите.
