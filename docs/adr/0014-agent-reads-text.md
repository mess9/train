# 0014. Агент читает плотный текст, пишет JSON; журнал тренера

Дата: 2026-11-12. Статус: принято. Заменяет часть 0005 про чтение, дополняет 0002.

## Контекст

Перед планом агент собирал контекст сам: `compare` каждой тренировки — JSON до ~70 КБ, — и
одноразовый скрипт сжимал его в текст; историю упражнения — по одной прошлой тренировке
(`exercise last`), раньше окна ничего не видно; решения прошлых разборов («держим 15 кг до 12
повторов») нигде не записаны и выводятся заново. В JSON большая часть объёма — повторяющиеся
ключи (`"recordType": "WEIGHT_REPS"` у каждого подхода), а не факты.

## Решение

- **Чтение — текст, запись — JSON.** `gym compare`, `history`, `weeks`, `journal`, `brief`
  печатают плотный текст: подходы с одной нагрузкой — группой (`12кг: 10✕ 10✓ · 14кг: 8✓`), цель —
  с множителем (`3× 12кг 8–10 r3`), оценки — значками приложения. Легенда — `AGENT_TEXT_LEGEND`
  в `--help`. `--json` — прежний JSON для скриптов. Планы агент по-прежнему пишет JSON по схеме.
- **Рендер в core** (`AgentText.kt`), не в CLI: формат проверяется тестами core, и его можно
  показать где угодно. Сервер отдаёт модели JSON (ADR 0002 — аналитика на сервере), CLI рисует.
- **История упражнения** (`GET /api/history`, `history()` в core): последние N тренировок
  целиком (по умолчанию 8), раньше — лучшая за месяц; лучший подход по оценке силы (Эпли для
  веса × повторы, с весом тела для подтягиваний), тренд к прошлой, рекорд и сколько тренировок
  после него; `since` — вместо N все тренировки с дня. Без id — упражнения основных блоков за
  месяц: «что сейчас в программе».
- **Недели** (`GET /api/stats/weeks`, `weeks()`): по строке на неделю с понедельника — тренировки,
  минуты, оценки рабочих подходов, объём, вес, группы мышц; пустая неделя — тоже строка.
- **Журнал тренера** — отдельная таблица `journal_entry`: день, решение, обоснование, условие
  пересмотра — три обязательные колонки, а не один текст, чтобы решение без опоры и без выхода
  нельзя было записать; ссылки на тренировку, план, упражнения. Не в профиле (там правила и
  ответы владельца, а не поток решений), не в тренировке (решение бывает про программу целиком).
  Запись про упражнение видна в его истории. Решение не переписывают: пересмотр — новая запись
  с `revises`, у старой сервер считает `revisedBy` (последняя живая пересматривающая), и она
  уходит из действующих (`?active=true`). Правка по id — для опечаток. Телефон журнал не
  синхронизирует; удаление — в корзину, `?deleted=true` и `restore` — вернуть.
- **`gym brief`** — всё перед планом за один вызов, окно — месяц: профиль, планы, журнал
  (действующие решения любой давности и все записи окна), 8 недель, последняя тренировка и до
  двух неразобранных целиком (неразобранная — нет записи журнала с её `workoutId`, остальные —
  списком id), история программы: тренировки окна целиком, раньше — лучшая за месяц. Старше
  окна — отдельными вызовами.

## Почему

Текст той же тренировки — 3,5 КБ против 20 КБ JSON при тех же фактах. Агент не пишет скрипты,
а окно истории шире: месяцы до окна видны выборкой, плато — числом. Журнал делает решения
переносимыми между сессиями, а пересмотр по ссылке сохраняет, как решение менялось. Окно
brief — месяц: две недели — это 4–6 тренировок, меньше одного цикла прогрессии; действующие
решения нужны любой давности — это текущее состояние программы.

## Цена

Два формата вывода. Текст — для чтения, а не для разбора: скрипту нужен `--json`.
