# 0013. Импорт истории — `gym import` через API синхронизации

Дата: 2026-11-05. Статус: принято. Пункт 3 «Импорт истории» в `docs/PLAN.md`.

## Решение

- **Формат — тот, что выдаёт API.** Каталог с тремя папками; файлы `*.json` читаются по имени:
  - `plans/` — план `{id, date, title?, body}`; вывод `gym plan get` подходит как есть, поля
    вывода (`version`, `status`…) отбрасываются;
  - `workouts/` — `{workout, sets, measurements?}`, то есть вывод `gym workout get`: тренировка с
    раскладкой, подходы, замеры этой тренировки;
  - `measurements/` — замер или массив замеров (вывод `gym measure list`).

  Разбор строгий, как у `plan put` (`decodeStrict`): незнакомое поле — ошибка с путём. Всё
  читается и проверяется до первой записи: подход ссылается на свою тренировку и на строку её
  раскладки, ID не повторяются, все упражнения есть в справочнике. Ошибка — ничего не записано.
- **Конвертер — в `import/`, данные — нет.** `import/hevy_gymkeeper.py` читает выгрузки Hevy
  (тренировки, шаблоны, фото, `measurement_data.csv` с замерами) и GymKeeper из личного хранилища и
  пишет каталог этого формата во временную папку вне репозитория; `gym import` его заливает.
  Выгрузки и готовый каталог — личные данные, а main пушится в Gitea: в репозиторий они не
  попадают, `.gitignore` закрывает `import/*/` и `import/*.json`. Каталог по тем же выгрузкам
  собирается заново с теми же ID. Сопоставление упражнений с справочником делает конвертер; чего
  в справочнике нет, добавляют `gym exercise add` до импорта, конвертер называет такие упражнения.
- **ID — UUIDv5** от `"<источник>:<исходный ID>"` в пространстве имён
  `fde5d64b-7ed4-44f6-82c5-8df8aea58b88` (`IMPORT_NAMESPACE` и `importId` в `cli`). Так же
  выводятся ID блоков, строк раскладки и целевых подходов: повторная конвертация даёт те же ID,
  и повторная заливка попадает в те же записи, а не в копии.
- **Запись — через существующие эндпоинты**, без отдельного API импорта: `PUT /plans/{id}`, затем
  `PUT /workouts/{id}` и `PUT /workouts/{id}/sets/{setId}`, затем `PUT /measurements/{id}`.
  Порядок нужен серверу: тренировка ссылается на план, подход — на тренировку, замер — на
  тренировку. `planVersion` тренировки, если не задан, — версия плана после импорта.
- **Сначала чтение.** Каждую запись `gym import` сперва читает с сервера:
  - нет — создаёт: `baseRev = 0`;
  - такая же (без `rev` и дня, которые считает сервер) — не трогает;
  - другая — не трогает и сообщает `differs`, код выхода 1; с `--update` — перезаписывает с
    `baseRev` текущей версии, прежняя уходит в `revision_log` (ADR 0007).

  `opId` — UUIDv5 от вида записи, `baseRev` и содержимого: если ответ потерялся, повтор той же
  отправки сервер узнаёт и вторую версию не пишет. Начатый план сервер не меняет (`409`), и
  импорт его не меняет даже с `--update`. `--dry-run` только читает и выдаёт тот же отчёт.
- **Отчёт — JSON**: `{dryRun, created, updated, same, differs, records: [{kind, id, action, note?}]}`.
- **Фото — отдельно**: `gym photo add --id <UUIDv5> --at … --workout …`. Повтор с тем же файлом
  под тем же ID сервер не дублирует (ADR 0010).

## Чего у источника нет — как заполняется

Импорт записывает то, что есть в источнике, и не дописывает недостающее «для красоты». Два
исключения, без которых история не работает:

- **`doneAt` подхода.** `exercise last` и `compare` берут последний подход по `done_at`, а
  `compare` ещё и только до старта тренировки — без времени подход в них не попадает. Hevy и
  GymKeeper времени подхода не дают. Конвертер раскладывает отметки равномерно между стартом и
  финишем в порядке выполнения: в круге — по проходам. Время отдыха по таким отметкам — не факт.
- **Тип записи и сторона** подхода — по смыслу источника, а не по справочнику. Скакалку в Hevy
  владелец вёл в поле секунд, а писал прыжки: у подходов `REPS`, хотя цель плана — секунды.
  Если бы повторы в источнике были суммарные на обе стороны, у подхода было бы
  `perSide = false` при «на сторону» в справочнике; в истории 2026-10 таких нет — владелец пишет
  повторы на одну сторону.
- **Время фото.** Hevy не отдаёт дату съёмки, только карточку тренировки: время фото — конец
  этой тренировки, в заметке фото сказано, что дата съёмки неизвестна.

Происхождение записи — в комментарии тренировки (`comment`): источник и исходный ID.

## Почему

- Отдельный эндпоинт импорта дублировал бы проверки владельца, версий и связей, которые уже
  есть у синхронизации и проверены тестами. Через те же `PUT` импорт — ещё один клиент вроде
  телефона.
- Формат вывода API — уже документированный и строгий. Его понимает агент, и `workout get` →
  правка → `import` работает без отдельного описания.
- Без чтения перед записью повтор с `baseRev = 0` давал бы `409` на каждую уже залитую запись, и
  отличить «уже залито» от «поправлено на телефоне» было бы нечем. После чтения правка с телефона
  не затирается молча: нужен явный `--update`.

## Отвергнуто

- **Импорт на сервере** (загрузить архив Hevy). Сервер узнал бы форматы чужих приложений, а
  личные выгрузки оказались бы в его логах и временных файлах.
- **UUIDv7, как у остальных записей.** Каждая конвертация давала бы новые ID: вторая заливка —
  копии тренировок.
- **Перезапись без проверки** (`baseRev` из текущей версии всегда). Затирала бы правки владельца
  на телефоне при каждом повторе.
