# 0007. Синхронизация телефона и сервера

Дата: 2026-11-01. Статус: принято.

## Решение

**Офлайн-старт против правки плана.** У плана есть `version`: сервер увеличивает её при
каждой правке и хранит все версии неизменными. Тренировка при старте копирует в `layout`
снимок целей и запоминает `planVersion`. Подходы ссылаются на цели внутри снимка, а не на план.
Если к синхронизации версия на сервере уже другая:
- тренировка принимается целиком;
- план помечается «начат с версии N, правка до M не применилась»;
- `compare` сравнивает со снимком;
- что делать с новой версией, решает агент.

**Очередь.** Хранит не журнал операций, а последнее состояние каждой сущности. Цепочка
«отметил → снял → отметил» уходит одной отправкой. Всё отправляется через `PUT` полного
состояния, `DELETE` для синхронизируемых сущностей нет:
- снятие отметки — `done: false`;
- удаление — `deleted: true`. Это надгробие: запись остаётся на сервере вместе со своей версией.

**Версии.** У каждой записи есть `rev`, его считает сервер. Клиент отправляет `baseRev` и `opId`.
- Тот же `opId` пришёл повторно, например потерялся ответ → `200` с текущим состоянием, без изменений.
- `baseRev` не совпадает с текущим `rev` → `409` с текущим состоянием. Заголовок `X-Op-Id`
  называет `opId` этой версии.
- Тренировка активна → побеждает телефон: клиент повторяет запрос с новым `baseRev`, а
  перезаписанная версия уходит в журнал `revision_log`.
- Тренировка завершена → побеждает сервер, телефон показывает «обновлено».
- Версия сервера — своя же отправка, ответ на которую потерялся, а запись с тех пор
  поправили → тоже побеждает телефон. Например, старт дошёл, ответ нет, потом финиш. Очередь
  помнит `opId` прежних состояний записи (`replaced`) и узнаёт свою версию по `X-Op-Id`.
- Первая запись ID атомарна: из двух одновременных вторая получит `409`, чужая — `404`.

**Время.** Часы клиента в разрешении конфликтов не участвуют. `doneAt` — это данные для порядка
и отдыха. Сервер дополнительно пишет `receivedAt`.

**Активные тренировки.**
- Две вкладки: писать может только та, что держит Web Lock `active-workout`.
- Два устройства офлайн: сервер принимает обе тренировки. Главная показывает «две активные —
  какую закрыть?».

**Локальное хранение.** Активная тренировка и очередь лежат в одном ключе localStorage и
пишутся одним синхронным `setItem` на каждое действие пользователя, до обновления экрана.
Кэш планов хранится отдельно, его можно потерять. На IndexedDB переходим, только если
перестанем помещаться.

## Почему

Правило «побеждает позднее клиентское время» ломается в нескольких случаях: часы меняются,
ответ теряется, запись удаляют и снова создают. Версия от сервера плюс идемпотентный `opId`
закрывают эти случаи без распределённых часов.

Писатель почти всегда один: во время тренировки это телефон, а агент правит только завершённое.
Поэтому правило «кто побеждает» хватает определить по состоянию тренировки.
