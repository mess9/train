# 0006. Тело плана — jsonb, подходы — строки

Дата: 2026-11-01. Статус: принято.

## Решение

- **План** — строка с датой, `version` и пометками. Само тело лежит в `plan_revision(plan_id,
  version, body jsonb)`. Версии неизменяемы, каждая правка создаёт новую. Внутри `body` у
  каждого блока, упражнения в блоке и целевого подхода есть свой UUID.
- **Тренировка** — строка: старт, финиш, комментарий, `plan_id`, `plan_version` и `layout jsonb`.
  - При старте в `layout` копируется **снимок** целей этой версии плана.
  - Дальше `layout` меняется на ходу: замена (`replacedFrom`), добавление, порядок,
    тип записи по умолчанию.
  - Подходы ссылаются на цели внутри снимка.
- **Фактический подход** — строка `workout_set`. Каждый факт хранит, как его понимать:
  - упражнение, ключи блока и элемента из `layout`, номер ячейки, ссылку на цель;
  - **свои** `record_type` и `per_side`;
  - значения, оценку, `doneAt`;
  - поля синхронизации: `done`, `deleted`, `rev`, `op_id`.

  Тип в `layout` — только значение по умолчанию для новых подходов.
- **Правка справочника** на старые факты не влияет: тип, сторона и упражнение хранятся в самом
  факте. Исключения — названия и маппинг мышц: их исправление намеренно меняет и статистику
  прошлого.

## Почему

Агент пишет план целиком одним JSON. После старта тренировка опирается на свой снимок, поэтому
раскладывать план по таблицам ради правки по частям не нужно. Схема плана одна — OpenAPI, в SQL
её не дублируем.

Подходы, наоборот, запрашиваются по отдельности: «прошлый результат упражнения X на подходе N»,
история упражнения, объём. С телефона они приходят поштучно через идемпотентный upsert
(ADR 0007), и смысл каждого должен сохраниться, даже если раскладку и справочник потом поменяют.
